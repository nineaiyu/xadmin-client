# 图标子集 chunk 体积：量化与裁剪决策记录

> 来源：前端审查观察项 1（图标子集 chunk 偏大）的暂缓项处置——不采信「偏大即裁」，
> 先量化首屏影响与懒加载边界，再给出可落地裁剪方案与决策门槛。基线 v5.0.2。
> 关联机制：`scripts/gen-icon-subset.mjs`（构建期子集化，fail-closed）、
> `src/components/ReIcon/src/iconRegistry.ts`（按 set 懒加载）、
> `src/components/ReIcon/data.ts`（选择器候选面）。

## 一、量化事实（2026-11-03 实测）

`node scripts/gen-icon-subset.mjs --report`（引用面 = 选择器候选 ∪ 代码 `~icons` 引用 ∪ 服务端种子）：

| 集合     | 子集图标数 | 其中选择器候选 | 代码引用 | 种子引用 | 全集合 raw | 子集 raw | 子集 chunk gz（构建实测） |
| -------- | ---------- | -------------- | -------- | -------- | ---------- | -------- | ------------------------- |
| ep       | 293        | 293            | 45       | 43       | 113KB      | 109KB    | 30.09KB                   |
| ri       | 2536       | **2535**       | 31       | 9        | 1110KB     | 740KB    | **182.47KB**              |
| fa-solid | 1023       | **1023**       | **0**    | **0**    | 681KB      | 627KB    | **195.47KB**              |

两个关键读数：

1. **ri 与 fa-solid 的体积几乎全部来自选择器候选面**（代码 + 种子合计仅 40 / 0 个）；
   ep 的候选即 Element Plus 图标全集（本就只有 293 个），无可裁空间。
2. **fa-solid 在仓内零消费**：代码与种子都不引用，chunk 存在的唯一原因是
   「菜单管理 → 图标选择器」把它列为可选集合。

## 二、首屏与懒加载边界（结论：首屏零影响）

图标集懒加载只在两个入口触发（`iconRegistry.ensureIconSet`）：

| 入口                       | 触发时机                                                  | 命中集合     |
| -------------------------- | --------------------------------------------------------- | ------------ |
| `localIcon.ts`             | 渲染一个**未随包注册**的图标名（菜单元数据形如 `ep:xxx`） | 按图标名前缀 |
| `Select.vue`（图标选择器） | 管理员打开选择器的某个集合页签                            | 该页签集合   |

种子菜单图标与代码在用图标全部经 `offlineIcon.ts` **随包注册**（`~icons/<set>/<name>?raw`
静态 import，树摇后进入口 chunk，几十个图标合计仅数 KB）——因此**默认部署的首屏与日常
导航不加载任何子集 chunk**。`ri`（182KB gz）与 `fa-solid`（195KB gz）只在管理员打开
对应选择器页签（或存量菜单选了非注册图标）时按需加载一次，属管理面低频操作。

**结论：图标 chunk 不在首屏关键路径上，「首屏变快」不是裁剪的收益来源。**

## 三、裁剪方案与风险（需要产品决策，暂不执行）

裁 chunk 的唯一杠杆是裁 `data.ts` 候选面——子集**按构造包含选择器可出的每个图标**
（一致性不靠对账靠生成：用户选到的图标必然离线可渲染，这是内网可用性的硬约束，
不能把候选与子集拆开各自维护）。因此「裁候选面 = 决定用户能选哪些图标」，属产品能力取舍。

| 方案                                                                      | 动作                                                 | 收益                                                                                                   | 风险 / 前置                                                                                                                                                                                       |
| ------------------------------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. 维持现状（默认）                                                       | 不动                                                 | 零风险；管理面一次 182/195KB gz 按需加载                                                               | 无                                                                                                                                                                                                |
| B. 精选候选面（**已做成可开启的构建选项**，2026-11-04，开启步骤见 §三.1） | 按 `scripts/icon-candidates.curated.json` 裁剪候选面 | chunk 实测：ri 182.47KB → 26.1KB gz（候选 2535 → 402）；fa-solid 195.47KB → 8.2KB gz（候选 1023 → 52） | ① 精选清单是产品口径（含 fa-solid 去留）；② **存量菜单兼容**：客户库里已选被裁图标的菜单会渲染空白（`gen-icon-subset` 只扫仓内种子，扫不到客户运行库），需配套「已用图标保底集」（§三.1 第 3 步） |
| C. 拆 data.ts 出首屏闭包                                                  | 候选清单改动态加载                                   | 不减 chunk 本身，只影响选择器首开时延                                                                  | `data.ts` 已不在入口闭包关键路径，收益趋零（未实施）                                                                                                                                              |

### 3.1 方案 B 的开启步骤（默认关闭，零行为变化）

机制：`gen-icon-subset.mjs` 与选择器（`ReIcon/src/Select.vue`）消费**同源生成的**
候选面产物（`data/picker-candidates.json`，gitignore）——默认档与 `data.ts` 全候选
面逐名一致；curated 档按清单裁剪，子集与运行时候选同源收缩，一致性不靠对账靠生成。

1. 定稿产品清单：编辑 `scripts/icon-candidates.curated.json`（形状
   `{"ri": [...], "fa-solid": [...]}`；**键缺席 = 该集合保持全候选面**——ep 只有
   293 个通常无需裁剪；清单内名字不在候选面会让构建 fail-closed 报错并列名——
   仓内现有内容是按常用语义自动生成的起点清单，非最终产品口径）。
2. 开启构建：`ICON_CANDIDATES_CURATED=1 pnpm build`（prebuild 与 vite 同进程继承
   该变量；只重生成子集时 `ICON_CANDIDATES_CURATED=1 node scripts/gen-icon-subset.mjs`）。
3. **存量客户库配套（风险②的落地口径）**：`gen-icon-subset` 只扫仓内种子，扫不到
   客户运行库已选的图标——上线前先从真实库导出在用图标并集并**并入清单**：

   ```sql
   -- PostgreSQL：导出存量在用图标（菜单引用面；如有其它引用面按需扩展）
   SELECT DISTINCT meta->>'icon' FROM system_menu WHERE meta->>'icon' LIKE 'ri:%';
   SELECT DISTINCT meta->>'icon' FROM system_menu WHERE meta->>'icon' LIKE 'fa-solid:%';
   ```

   （代码与仓内种子引用图标由生成器自动保底，不需要进清单。）

4. 验证：curated 构建产物里 `ri` / `fa-solid` 子集 chunk 明显缩小；菜单管理 →
   图标选择器候选数与清单一致；任选一个图标能离线渲染。

已知约束：清单值不得为空数组（整套下线需先改造 `iconRegistry` 的静态懒加载链路，
构建会 fail-closed 说明）；选择器对「已选图标不在候选面」的存量值按空页签展示兜底，不报错。

## 四、决策记录

- **当前决策：维持方案 A（现状，默认全候选面）**。理由：首屏零影响（§二）、加载场景为
  管理面低频、裁剪收益只作用于低频路径，而风险面（存量菜单空白）需要产品口径与兼容配套。
- **方案 B 机制已就绪**（2026-11-04）：清单 + `ICON_CANDIDATES_CURATED=1` 构建开关
  落地，产品给出「可选图标范围」口径后可一步启用（清单定稿即开），不再需要代码改造。
- **触发条件（满足任一则启用方案 B）**：
  1. 产品给出「可选图标范围」的明确口径（含 fa-solid 去留）；
  2. 出现对弱网管理环境的明确反馈（选择器首开耗时被投诉）；
  3. 移动端管理形态（手机维护菜单）成为受支持场景。
- 启用时按 §三.1 步骤执行（含存量库在用图标回灌），不要直接改 `data.ts`。
